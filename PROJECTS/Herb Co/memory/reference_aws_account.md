# reference_aws_account

**Last Updated:** 2026-07-01

**Summary:** How Webapper accesses AWS for managed/client accounts (the pattern used on Herb Co and other managed engagements). This file intentionally contains **no** account IDs, role ARNs, or secrets — those live in access-controlled systems and the internal tooling repo, never in this template.

## Access pattern (chained AssumeRole via IdC SSO)

All access goes through **Webapper IdC SSO** — there are no per-account usernames/passwords.

- **Console:** AWS access portal → Applications tab → pick the account. One click; sessions are time-limited.
- **CLI:** chained AssumeRole using the `ama-*` profile pattern, sourced from a management profile (`ama-mgmt`).
  - **Daily login:** `aws sso login --profile ama-mgmt`
  - **Default for read/look-around:** the project's read-only `ama-*-ro` profile
  - **For deploys / IaC / secret writes:** the project's `ama-*-admin` profile
- Profiles are generated by the internal AWS-access tooling (see the managed-agents tooling repo). Any external IDs or secrets are stored locally, gitignored, and never committed.

## Guardrails

- Root accounts are locked; MFA lives in a password manager and is not used day-to-day.
- CloudTrail is enabled on managed accounts — actions are logged.
- Account-specific IDs, role ARNs, CloudTrail names, and provisioned users are **not** recorded here; retrieve them from access-controlled Jira/Confluence or the tooling repo.

## Common gotchas

- "Unable to locate credentials" → `aws sso login --profile ama-mgmt`
- "SSO session expired" → same as above (sessions are time-limited)
- "AccessDenied on AssumeRole" → check the ExternalId in `~/.aws/config` against your local secret file
- "Could not connect to endpoint" → set the correct `--region` (or put it in the profile)
